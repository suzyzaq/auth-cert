SCS 候选回流闭环

Dify 复核节点 → 宿主机 Webhook → scs_backfill.py → 容器热重载 · 品牌主数据自增长
结论：把 POST /api/brand/normalize 返回的 SCS 候选（scs_candidate）经 Dify 人工复核确认后， 由 Dify「请求」节点 POST 到宿主机常驻的 backfill_webhook，自动写回 matcher.db 并热重载， 后续请求直接命中本地库、不再每次查 SCS。
全流程
① Dify 复核
normalize 返回 scs_candidate → 人工确认是否同品牌 + 指定 standard_brand
→
② Webhook
宿主机 :8900 常驻，Bearer 鉴权，收确认清单
→
③ backfill
scs_backfill.py --apply 写宿主机 matcher.db
→
④ reload
调容器 /api/brand/reload 热重载内存索引
写库在宿主机（绕开容器 :ro）reload 走容器内端点幂等：已存在自动跳过
Dify 节点设计
序号节点类型配置要点
①品牌标准化HTTP 请求POST :8000/api/brand/normalize · Header Authorization: Bearer <token> · Body 含 attachment_values/source_values
②是否 SCS 候选代码 / IF 分支取 needs_manual_review 与 match_type；为候选 → 走人工复核，否则直接出结论
③人工复核确认人工复核 / 表单展示 scs_candidates（firm_code/firm_name）；确认是否同品牌 + 填 standard_brand
④拼装确认清单代码节点转成 [{firm_code,firm_name,standard_brand}]，对齐 scs-confirm.schema.json
⑤触发回流HTTP 请求POST :8900/backfill · Header Authorization: Bearer <token> · Body = 确认清单
⑥回流结果结束 / 钉钉读 applied/skipped/reload_ok；失败则钉钉告警

Webhook API（宿主机 :8900）
请求 POST /backfill · Bearer 鉴权 · Body：
[
  {"firm_code": 182805, "firm_name": "洁佳人",   "standard_brand": "洁佳人"},
  {"firm_code": 7563,   "firm_name": "惠普企业版", "standard_brand": "惠普/HP"}
]
// 或包一层： {"items":[...], "dry_run":false, "reload":true}
响应：
{
  "ok": true,
  "applied": 2, "skipped": 0, "dry_run": false,
  "reload_done": true, "reload_ok": true,
  "log_file": ".../.scs_backfill_log/backfill-20260726-220626.json",
  "detail": "[APPLIED] 已写入 2 条，跳过 0 条。"
}
宿主机启动（Dify 云端访问需 --host 0.0.0.0 + 内网穿透）：
cd brand-normalize-service
python scripts/backfill_webhook.py
# 或显式
python scripts/backfill_webhook.py --host 0.0.0.0 --port 8900 \
  --db C:/Users/Lenovo/.workbuddy/skills/brand-matcher/data/matcher.db \
  --token <BRAND_API_TOKEN>
约束与边界（必读）

● 写库必须在宿主机：容器内 matcher.db 是 :ro 只读挂载，不能在容器内写。backfill_webhook 跑在宿主机，写的是宿主机真实 matcher.db 路径。

● 云端 Dify 无法直连宿主机：须让 Dify 能访问宿主机 :8900。同内网/私有化用内网 IP；云端用内网穿透（frp/ngrok/Cloudflare Tunnel）；同机 Docker 用 host.docker.internal:8900。

● 鉴权与安全：webhook 用 Bearer <BRAND_API_TOKEN>（与 normalize 同一 Token）。默认仅监听 127.0.0.1；暴露公网时务必在穿透层加来源限制/二次鉴权。

● 幂等：已存在的 firm_name（brands 或 brand_alias）自动跳过，重复触发安全。

● 留痕：每次调用落盘 .scs_backfill_log/backfill-<ts>.json（入参+结果），便于追溯。

● 备选触发：若不想暴露宿主机端口，可走钉钉 AI 表格中转——Dify 写「SCS回流待处理」表，宿主机 WorkBuddy 定时轮询 → backfill → 回写状态（本机可达性无忧，适合长期生产）。

下一步建议

1. 穿透/可达性：确定 Dify 部署形态，配好 :8900 的访问方式（同网 IP / 穿透 / host.docker.internal）。

2. Dify 工作流落地：按上表 6 节点搭建，④代码节点对齐 scs-confirm.schema.json，先 dry_run:true 验证链路再放开写库。

3. 钉钉中转备选：若走中转台路线，设计「SCS回流待处理」表字段（firm_code/firm_name/standard_brand/审核单号/status/回流结果）。

4. 回流案例沉淀：确认清单可反向沉淀为「SCS候选→确认」案例库，校验 brand-recognition 召回质量。

5. 监控：webhook 返回 reload_ok:false 或 applied:0 时接入钉钉告警。
