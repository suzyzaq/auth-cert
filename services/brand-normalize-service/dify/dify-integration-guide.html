二、三种接入形式对比

按「开发量 / 可发布性 / 适用场景」选择。推荐形式一（零开发，现成 OpenAPI 即可导入）。

形式开发量是否可发布为「插件」适用场景
① 自定义工具 · OpenAPI 导入零开发导入后在当前工作区作为工具，可跨应用复用绝大多数场景首选；直接复用现成 openapi.json
② HTTP 请求节点零开发否（仅工作流内联）单工作流内临时调用，不想建工具
③ 原生插件 · Plugin SDK需建插件工程是（.difypkg / 市场发布）要版本化、上架 Dify 插件市场、团队/客户分发

三、形式一：自定义工具（OpenAPI 导入）· 推荐

直接用项目已有的 dify/brand-normalize-tool.openapi.json（已修复可导入）。

  1. 部署服务并获得可达地址（见第五节可达性）。假设 http://10.x.x.x:8000。
  2. 打开 brand-normalize-tool.openapi.json，把 servers[0].url 的 http://YOUR_HOST:8000 改为真实地址。
  3. Dify Studio → 工具 → 自定义 → 导入 OpenAPI 规范 → 粘贴/上传该 JSON。
  4. 鉴权：Dify 会读取 securitySchemes.bearerAuth。在工具鉴权设置选 API Key → Header 名 Authorization → 值 Bearer <你的 BRAND_API_TOKEN>。
  5. 保存后，在任意 聊天流 / 工作流 中添加该工具节点，映射变量：品牌 ↔ attachment_values/source_values；品类 ↔ product_name/client_category。
  6. 运行测试：输入「茶杯」→ 应得 kind3=陶瓷杯；输入「惠普/HP」→ matched_standard_brand_id=BRAND_000621。
★ 导入失败排查：若 Dify 报「无法解析规范」，多为 OpenAPI 版本或 securitySchemes 拼写——本项目已锁定 3.0.3 且确认拼写正确（见第六节）。

四、形式二：HTTP 请求节点（工作流内联）

不建工具、不发布，仅在单个工作流里直接打 HTTP。项目已有 dify/dify-http-node.md 模板。

HTTP 请求节点配置（点击展开）

// 品牌节点 Body 示例（变量来自上游节点）
{
  "task_type": "brand_standardization",
  "attachment_values": [ "{{#start.attachment_brand#}}" ],

品牌节点与品类节点 完全独立——一个超时/报错不影响另一个。输出变量提取见 dify-http-node.md。

五、形式三：原生插件（Plugin SDK · 可市场发布）

若要把它作为「插件」正式上架 Dify 插件市场或团队分发，用 dify_plugin SDK 封装成 .difypkg。本服务作为后端被调用（或内嵌核心层）。

插件工程骨架（点击展开） 
ofs-normalize-plugin/
├── manifest.yaml        # 插件元信息（name/version/author）
├── provider/
│   └── ofs_normalize.yaml   # 工具提供方声明（指向 endpoints/tools）
└── tools/
    ├── brand_normalize.py     # Tool 类：组装请求 -> 调本服务 HTTP
    └── category_normalize.py  # Tool 类：同上（独立，隔离）
# 关键：Tool 内部用 requests/urllib 打本服务
#   POST {service_url}/api/brand/normalize
#   Header Authorization: Bearer {settings.token}
# 打包：dify plugin package .  ->  ofs-normalize-plugin.difypkg
# 安装：Dify 插件管理 -> 本地安装/市场发布

与原生插件相比，形式一（自定义工具）几乎零成本且能力等价；仅在「要版本化/市场上架/跨租户分发」时才值得做形式三。

六、部署可达性（硬前提 · 任何形式都一样）

⚠ Dify 必须能网络访问到 brand-normalize-service 的部署地址，否则三种形式全部失败。容器化部署时 matcher.db 是 :ro 只读挂载，写库须在宿主机。
部署形态可达方案
Dify 与服务同集群 / 同内网直接用内网地址（如 http://10.x.x.x:8000）
服务在宿主机，Dify 云端frp / ngrok 穿透，或用 host.docker.internal（Dify 也容器化且同主机）
不确定网络 / 长期生产钉钉 AI 表格中转：Dify 写「标准化待处理」表 → 宿主机 WorkBuddy 定时轮询 → 调服务 → 回写状态（本机可达性无忧）
